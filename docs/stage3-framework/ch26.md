# 26 - LangGraph 多智能体与 A2A

---

**本章课程目标：**

- 理解 **多智能体（Multi-Agent）** 解决什么问题，以及它和单智能体之间的边界。
- 理解 **A2A（Agent-to-Agent）** 与 **MCP（Model Context Protocol）** 的区别——前者偏代理协作，后者偏工具 / 资源接入。
- 掌握多智能体常见模式：**Subagents / Handoffs / Router / Skills / Custom Workflow**，能结合 LangGraph 做基本选型。

**学习建议：** 先分层再写代码：多智能体是应用内分工，MCP 是外部能力接入，A2A 是不同智能体系统之间的协作。第一遍不必背 A2A 规范细节，先把概念层级拆开。

**官方文档与资源**：详见 [工具导航与参考资料索引 - LangGraph](/guide/resources#LangGraph)、[工具导航与参考资料索引 - 工具调用、mcp与智能体](/guide/resources#工具调用、mcp与智能体)。

## 1、A2A 协议与多智能体架构

### 1.1 概述

本章同时涉及 **LangGraph 多智能体**、**A2A**、**MCP**、**Supervisor**、**Handoff**、**Skills** 等概念。先把它拆成三层：

- **多智能体**：一种系统设计思路，指多个 Agent 分工协作完成任务
- **LangGraph**：一种实现多智能体工作流的图式编排框架
- **A2A**：一种让“不同 Agent 系统之间”可以标准化通信与协作的协议

即：**多智能体**是目标，**LangGraph**是应用内编排手段，**A2A**是跨系统协作协议。
### 1.2 多智能体定义

多智能体指的是：**把复杂任务拆给多个专精的 Agent，让它们分工、路由、协作，共同完成整体任务。**

与单智能体相比，核心变化不在数量，而在于角色分工、上下文隔离、控制流显式编排。例如：

- **单智能体**：一个 Agent 同时负责查航班、订酒店、回答用户、决定流程
- **多智能体**：一个主管 Agent 负责调度，航班 Agent 只管航班，酒店 Agent 只管酒店

多智能体适合的场景：

- 工具太多，一个 Agent 已经选不过来
- 领域太多，单个 Agent 上下文太臃肿
- 任务天然可以拆成多个角色
- 希望不同团队各自维护不同能力模块

### 1.3 为什么不是什么任务都需要多智能体

LangChain 官方多智能体文档明确指出：**不是每个复杂任务都需要多智能体。**

开发者声称需要 multi-agent 时，实际想要的往往是：

- 更好的上下文管理
- 更清晰的模块边界
- 更高效的并行化
- 更稳定的任务分工

如果任务本身简单，一个单智能体加上合适的工具、提示词和工作流就已经够用。

判断标准是：**多智能体不是默认选择，而是在单智能体已经吃力时才值得引入。**

### 1.4 A2A 协议定义

A2A 全称 **Agent-to-Agent**，是面向 Agent 系统互操作的开放协议，目标是让不同 Agent 以标准化方式发现彼此、发送任务、交换消息、返回结果。

A2A 的核心关注点是**Agent 之间如何协作**。几个核心概念：

- **Agent Card**：相当于 Agent 的“名片 / 能力说明”
- **Task**：一项被发给远程 Agent 的任务
- **Message**：围绕任务交换的消息
- **Artifact**：任务过程或结果产出的内容

串成一条最小调用链：

1. **先发现 Agent**：调用方先读取 `Agent Card`，确认对方会什么、支持什么输入输出。
2. **再提交 Task**：把任务目标、上下文消息、必要参数发给远程 Agent。
3. **过程中跟状态**：长任务通常不是一次就结束，调用方会通过轮询、流式更新或通知拿到任务进度。
4. **最后取结果**：读取最终 `Message` / `Artifact`，把它当成另一套 Agent 的产出继续接到自己的系统里。

A2A 回答的核心问题：如何发现远程 Agent、了解其能力、提交任务、获取中间消息和最终结果。

作为**跨 Agent 系统的互操作协议**，A2A 天然偏向：

- 远程发现与能力说明
- 跨服务任务提交与跟踪
- 长任务状态更新
- 结果产物回传

这和后面要讲的 `Supervisor` / `Handoff` 不同——后者发生在**同一个应用内部的 LangGraph 图里**，重点是编排多个角色，而非让独立 Agent 平台按统一协议互通。

### 1.5 A2A 和 MCP 的区别

- **MCP**：Agent / 模型如何接入工具、资源、上下文（agent-to-tool / agent-to-resource）
- **A2A**：Agent 之间如何协作（agent-to-agent）

比喻来说：**MCP** 像修车厂的工具柜，解决维修工如何标准化使用工具；**A2A** 像不同岗位之间的协作机制，解决前台、维修工、配件采购、质检之间如何传任务和结果。

因此 MCP 不负责代理间协作，A2A 不负责工具暴露给模型。两者不互斥，可以同时存在于一个系统中。

> **术语约定：** 本章里说的“**LangGraph 多智能体**”默认指**应用内编排**，说的“**A2A**”默认指**跨系统 Agent 协作协议**。把这两个语境先分开，后续看 Supervisor、Handoff 和远程 Agent 协作时不容易混淆。

### 1.6 LangGraph 多智能体和 A2A 是什么关系

**LangGraph 多智能体不等于 A2A。** 在一个应用内部用 LangGraph 编排多个 Agent 协作，这是多智能体，但未必用到 A2A 协议。A2A 描述的是不同系统中的 Agent 跨进程、跨服务、跨平台的标准化协作。

关系总结：**LangGraph 多智能体**偏应用内编排，**A2A**偏系统间互操作。真实项目中的区分：

- 同一个团队在一个后端服务里，用 LangGraph 编排 `supervisor`、`research_agent`、`writer_agent`，这通常是**应用内多智能体**
- 你的系统要去调用另一个团队部署的远程法律顾问 Agent、报表 Agent、采购 Agent，这时更可能需要 **A2A**

核心判断：**LangGraph 解决本地编排问题，A2A 解决跨系统协作问题。**

### 1.7 LangChain 官方多智能体模式

LangChain 官方多智能体文档归纳了 5 类模式：

- **Subagents（子代理）**：主 Agent 把子 Agent 当工具来调
- **Handoffs（交接）**：不同 Agent 之间可以交接控制权
- **Skills（技能）**：单 Agent 按需加载专业上下文 / 技能包
- **Route（路由）**：先做路由，再把任务交给更合适的 Agent
- **Custom workflow（自定义工作流）**：直接用 LangGraph 自定义工作流，把上述模式混合起来

按控制流方向可以分为两大类：

- **一个主控中心在调别人**：Subagents、Router
- **控制权本身会转移**：Handoffs

`Skills` 较特殊，它让单 Agent 也能按需加载专业能力，不一定需要多智能体。

结合官方文档的典型取舍，实用判断：

- **Subagents / Router** 更强调上下文隔离，也更适合并行
- **Handoffs / Skills** 更偏状态连续，重复请求时往往更省调用
- **Custom workflow** 适合你已经知道标准模式不够，需要自己把路由、并行、循环、人工介入混起来

### 1.8 多智能体的常见结构形态

结合官方模式和 LangGraph 语境，多智能体常见形态包括：

- **单智能体（Single Agent）**：一个 Agent 负责整条任务链路，适合简单任务和教程起步。
- **Supervisor（主管型）**：一个中心主管负责决定调用哪个子 Agent，适合统一入口和集中调度。
- **Handoff（交接型）**：当前 Agent 可以把控制权交给别的 Agent，更适合角色切换和会话延续。
- **Router（路由型）**：先判断任务属于哪类，再把任务交给某个专门 Agent。
- **Network / Peer-to-peer（网络型）**：多个 Agent 更平等地交换信息，没有单一主管，适合研究、协作式问题求解。
- **Hierarchical（层级型）**：多层主管和子主管分层拆任务，适合复杂组织结构。

### 1.9 使用场景

选型时的判断依据：是否出现上下文过重、工具过多导致选择错误、任务可拆分为专业角色、需要并行、需要角色切换等问题。

速查表：

| 场景                         | 更适合的模式                 |
| ---------------------------- | ---------------------------- |
| 单领域、小任务、统一控制     | 单智能体 / Skills            |
| 多工具、多专业角色、统一入口 | Supervisor / Subagents       |
| 用户与不同角色来回切换       | Handoffs                     |
| 先分类再交给不同专家         | Router                       |
| 复杂系统、强流程编排         | Custom workflow（LangGraph） |

多智能体 / A2A 的实际落点是把大任务拆给多个专业角色协作。典型场景：

- **软件工程团队式协作**：规划 Agent 负责拆需求，代码 Agent 负责实现，测试 / Review Agent 负责运行验证和指出风险，最后由协调者汇总结果。
- **研究代理团队**：检索 Agent 收集资料，阅读 / 摘要 Agent 提炼证据，事实核查 Agent 做交叉验证，报告 Agent 输出带来源的结构化结论。
- **数据分析代理团队**：数据理解 Agent 解释指标口径，SQL / Python Agent 查询和计算，图表 Agent 生成可视化，业务解释 Agent 输出结论和建议。
- **并行代码任务**：当多个改动彼此独立时，可以让不同子 Agent 分别处理不同模块，再由 Supervisor 汇总 diff、测试结果和冲突风险。

这些场景的共同点是角色边界清楚、任务可拆分、过程需要协调或并行。如果只是单一领域的少量工具调用，优先从单 Agent 或固定工作流开始。

## 2、Supervisor 与 Handoff

### 2.1 为什么先学 Supervisor

Supervisor（主管型）是最适合入门的多智能体结构：有中心主管、控制流集中、接近项目经理分配任务的直觉，比 Network 等去中心化结构更易理解。

### 2.2 Supervisor 定义

Supervisor 模式：**一个主管 Agent 判断当前该让哪个子 Agent 执行，子 Agent 处理完后把结果交回主管。**

Supervisor 结构的核心在于：

- 主管是不是唯一调度中心
- 子 Agent 是否专注自己的狭窄领域
- 用户是否主要和主管交互

![Supervisor 架构：主管协调多个子 Agent](/images/26/26-2-1-1.gif)

这个模式特别适合：企业助手、旅行预订、客服分流、多部门协作场景。

![Supervisor 执行流程示意](/images/26/26-2-1-2.gif)

### 2.3 Supervisor 和 Subagents 关系

Supervisor 直接对应 LangChain 官方的 **Subagents（子代理）** 模式——把子 Agent 当工具调用。

这意味着用户始终与主管交互，所有路由由主管决定，子 Agent 充当高级工具。好处是上下文隔离强、统一控制强、工程边界清楚；代价是主管压力更大，有时多一层调用开销。

官方 `Subagents` 文档强调：调用子 Agent 的目的往往不只是分工，而是让它在**隔离的上下文窗口**里完成子任务，再把精炼结果返回主管。多智能体有时不只是分工，也是控制上下文规模的方法。

### 2.6 Handoff 定义

Handoff（交接型）和 Supervisor（主管型）容易混淆，但本质不同。

**Supervisor 的重心是中心调度，Handoff 的重心是控制权转移。** LangChain 官方文档因此把 `Handoffs` 单独列为一种模式。

### 2.7 Handoff 使用场景

Handoff 适合的场景：会话中角色真正切换、下一位 Agent 需要接着上下文继续与用户互动、不只是内部调用工具而是换一个角色接手。

例如：先由总客服接待再交给技术支持，先由通用顾问判断再交给航班专家，先由分析 Agent 完成分析再交给执行型 Agent。

需要注意：**不是所有角色切换都必须拆成多个 Agent。** 官方文档提醒，很多 handoff 场景用单 Agent + middleware / 状态机就能实现；只有角色、上下文、维护边界都清晰时，拆分收益才明显。

### 2.8 案例：SupervisorHandoff

这个案例展示的不只是主管调用子 Agent，而是如何显式构造交接、如何把状态和任务说明一起转给下一个 Agent。它是从 Supervisor 过渡到更灵活多智能体结构的桥梁。

重点观察：

- Handoff 不只是“调用另一个 Agent”，而是**明确指定下一跳**
- 交接时不仅传目标，还要思考**传什么上下文、保留哪些消息、是否构造新的任务说明**

官方 Handoffs 文档反复强调：多智能体真正的难点往往不在跳转本身，而在**上下文工程**。

### 2.9 Supervisor 和 Handoff 怎么选

判断标准：

- **始终需要中央主管统筹** → Supervisor
- **角色之间需要正式交接控制权** → Handoff

两者并不互斥，真实项目中常混用：

- 大结构上用 Supervisor 做统一调度
- 某些局部流程里允许 Handoff

## 3、Skills 与多智能体的边界

第 27 章专门讲 Agent Skills。本章只讨论与多智能体设计相关的边界：**Skills 能增强 Agent，但不是多智能体模式。**

### 3.1 Skill 不是一个独立 Agent

Skill 是可复用能力包，通常包含提示词、流程、模板、脚本和参考资料。它回答的是：

```text
遇到这类任务时，应该按什么方法做？
```

Agent 回答的是：

```text
当前任务该怎么拆、先做什么、调用什么工具、什么时候交给谁？
```

所以，Skill 不负责自主决策，也不负责和其他 Agent 协商。它更像一个可按需加载的专业说明书。主 Agent 或子 Agent 都可以挂载 Skills，但真正决定是否使用 Skill 的，仍然是 Agent。

### 3.2 单 Agent + Skills 什么时候更合适

许多任务不需要直接拆成多智能体。如果问题只是：

- 主提示词越来越长；
- 某类任务有固定 SOP；
- 多个任务复用同一套模板或规范；
- Agent 需要按需加载一大段专业上下文；
- 还没有明确的角色分工和权限隔离。

那优先考虑 **单 Agent + Skills**。例如，代码助手需要代码审查、测试修复、提交信息生成和文档改写等能力，可以先做成 Skills，不一定拆成 4 个 Agent。

### 3.3 什么时候才需要多智能体

出现以下特征时，才更适合升级为多智能体：

| 判断问题                         | 更可能的选择       | 原因                                 |
| -------------------------------- | ------------------ | ------------------------------------ |
| 只是复用一套流程、模板或检查清单 | Skill              | 能力复用即可，不需要独立角色         |
| 同一个 Agent 的提示词太长        | Skill              | 用按需加载减少主上下文压力           |
| 工具很多但任务角色仍然单一       | Skill + 工具治理   | 先整理能力和工具选择边界             |
| 已经有检索、分析、执行、审核分工 | 多智能体           | 角色职责不同，需要独立上下文         |
| 不同角色需要不同工具权限         | 多智能体           | 权限隔离比提示词复用更重要           |
| 需要显式交接控制权               | Handoff            | 当前对话状态要由另一个 Agent 接手    |
| 需要中心化调度多个专家           | Supervisor         | 主控 Agent 需要分发任务并汇总结果    |

三者关系：

```text
Supervisor 负责调度，Handoff 负责交接，Skills 负责沉淀可复用能力。
```

### 3.4 多智能体中怎么使用 Skills

Skills 和多智能体不是替代关系，而是组合关系。

一个真实项目里常见的设计是：

```text
主 Agent
├─ 通用 Skills：任务规划、报告写作、结果汇总
├─ 检索 Agent
│  └─ 检索 Skills：搜索策略、网页摘要、引用规范
├─ 数据库 Agent
│  └─ SQL Skills：表结构说明、查询规范、性能注意事项
└─ 审核 Agent
   └─ 审核 Skills：事实核查、安全检查、格式检查
```

这样做的好处是：

- 每个 Agent 的职责边界更清楚；
- 每个 Agent 只加载自己需要的 Skills；
- 通用能力可以复用，专业能力可以隔离；
- 不必把所有规则都塞进主 Agent 的 system prompt；
- 后续替换某个 Skill，不一定要重构整个多智能体架构。

**章节思考题：**

1. 单 Agent 什么时候应该升级成多 Agent？

   **参考思路：** 当任务有明确的专业角色分工、权限需要隔离、上下文过长或需要不同执行策略时，再考虑多 Agent。无目的的拆分会增加调试成本。

2. Supervisor 和 Handoff 的差别，可以用什么业务场景解释？

   **参考思路：** Supervisor 统一分派任务并汇总，Handoff 把控制权转给更合适的 Agent 继续处理。前者适合集中控制，后者适合角色间交接。

3. MCP、A2A、多智能体三者最容易混在哪里？

   **参考思路：** 多智能体是应用内角色协作，MCP 是外部能力接入协议，A2A 是跨系统代理协作协议。三者都涉及连接，但连接对象和层级不同。

4. 多 Agent 系统里，共享上下文应该越多越好吗？

   **参考思路：** 不一定。共享太少导致重复沟通，共享太多导致信息泄露和噪声增加。应按角色职责决定共享边界。

**本章小结：**

- **多智能体** 是让多个专精角色围绕一个任务分工协作，而非简单地多调几个模型。
- **A2A 和 MCP 不同**：MCP 偏 Agent 与工具、资源的接入；A2A 偏 Agent 之间的互操作和协作。
- **LangGraph 多智能体不等于 A2A**：LangGraph 做应用内编排，A2A 做跨系统协作。
- **Supervisor 和 Handoff** 是两种优先掌握的模式：前者中央调度，后者控制权转移。
- **Skills** 是能力工程化的补充层，帮助单 Agent 和多 Agent 系统都变得更可复用、更可维护。
- **多智能体设计的关键不只是拆角色，还包括上下文传递**——什么时候传完整上下文、摘要还是最小消息对，往往比角色数量更影响系统质量。
- **什么时候停在单 Agent**：如果没有明显的领域分工、权限隔离或上下文过载，单 Agent + Skills 或单 Agent + Workflow 更简单也更易调试。
- 学完本章后，应能判断何时需要多智能体；分清 LangGraph 应用内编排、A2A 跨系统协作、MCP 外部能力接入三层边界；知道 Supervisor、Handoff、Skills 各自解决什么问题。
