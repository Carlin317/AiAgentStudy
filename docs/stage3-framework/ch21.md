## 1、Agent 简介

### 1.1 定义

**Agent 是一种运行方式，不是某个特定模型或工具。** 它围绕用户目标，持续推理、调用工具、观察结果，直到任务完成。

最小结构包含四部分：

- **模型（Model）**：负责推理决策——理解目标、分析局面、决定下一步。
- **工具集（Tools）**：负责执行动作——查天气、查库存、调用 API、搜索文档、访问数据库。
- **运行循环（Loop）**：驱动多步迭代——想一步、做一步、看结果、再决定下一步。
- **状态（State）**：保存中间结果——本轮对话、工具返回、短期记忆。

入门阶段不需要关注长期记忆、复杂规划或多智能体协作——能读懂目标、判断何时调工具、根据结果继续决策，就已经构成一个可用的 Agent。

以上是最小结构。更完整的 Agent 架构还可能包含记忆、规划、反思等扩展能力，下图展示的是这种扩展后的能力拼图，而非与上面四部分一一对应。

![Agent 扩展架构示意：中心为 Agent，周邻 Memory（短/长期）、Planning（反思、自评、思维链）、Tools（日历、计算、搜索等）与 Action，强调多模块协同而非最小四元组一一对应（中文）](/images/21/21-1-1-2.png)

![Agent 扩展架构示意：中心为 Agent，周邻 Memory（短/长期）、Planning（反思、自评、思维链）、Tools（日历、计算、搜索等）与 Action，强调多模块协同而非最小四元组一一对应（英文）](/images/21/21-1-1-1.jpeg)

### 1.2 Agent 最常见的工作方式：ReAct

**ReAct = Reason + Act**，即先推理，再行动。

这是 Agent 最经典的运行循环：

1. **Thought / Reason（思考）**：当前要做什么，先想一步。
2. **Action（行动）**：如果需要外部能力，就调用某个工具。
3. **Observation（观察）**：拿到工具返回结果。
4. **继续循环或结束**：如果还没完成，就继续下一轮；如果信息足够，就给出最终答案。

ReAct 的核心就是：**先推理，再行动；根据行动结果，再继续推理。**

普通 LLM 调用是一次性的：用户提问，模型直接回答。Agent 则是多步的：用户提问，模型判断是否需要工具，调用工具，观察结果，再决定是否继续，最终回答。

下图对应这条循环：

![ReAct 模式：思考（Thought）→ 行动（Action）→ 观察（Observation）→ 根据结果继续循环或给出最终答案的闭环示意](/images/21/21-1-2-1.jpeg)

补充一点：**现代 Tool Calling Agent 不一定会把”Thought”完整显示给你看。**

很多时候你在代码里真正看到的是：

- `AIMessage` 里出现 `tool_calls`
- 工具执行后得到 `ToolMessage`
- 最后再出现一个普通 `AIMessage`

所以在今天的 LangChain / Tool Calling 语境里，ReAct 更应该被理解成一种**工作机制**，而不只是某种固定的 Prompt 模板格式。

**Agent 不只有 ReAct 这一种工作方式。**

ReAct 是最经典的一种，因为它最直观地展示了”Agent 为什么不只是一次回答”。真实项目里，常见的 Agent 形态还包括：

- **Plan-and-Execute**：先整体规划，再按计划逐步执行。
- **Router / Supervisor**：先判断该把任务交给哪个工具、哪个子 Agent、哪个流程。
- **Workflow + Agent 混合**：固定部分用工作流，遇到不确定节点时再让 Agent 决策。
- **Multi-Agent / A2A**：多个 Agent 分工协作，由一个主 Agent 或协调器统筹。
- **Human-in-the-loop**：关键步骤需要人工确认，Agent 不是全自动闭环。

总结：ReAct 是 Agent 最经典的工作机制，但不是唯一形态。本章先用 ReAct 入门，因为它最直观地体现 Agent 的核心价值。

### 1.3 Tool 与 Agent 的关系

**Tool（工具）** 是能力封装——`get_weather()`、`search_products()`、`check_inventory()`、`book_flight()` 这类函数或接口，每个只做一件事。

**Agent** 是决策者——负责判断要不要调工具、调哪个、先后顺序、是否重试、何时停止。

两者关系：**Tool = 能力；Agent = 决策 + 使用这些能力。**

| 对象      | 本质定位 | 含义                               |
| --------- | -------- | ---------------------------------- |
| **Tool**  | 能力层   | 我能做什么                         |
| **Agent** | 决策层   | 我什么时候、按什么顺序去用这些能力 |

有 Tool 不等于有 Agent。”查一下北京天气”这种一步问题，直接调天气工具就够了，不需要 Agent。

但如果问题变成：“帮我找最热门的无线耳机，再查库存，再告诉我哪款可以买”；“先订机票，再订酒店，再预约打车”；“先查知识库，再判断是否需要调外部 API，再整理成报告”。

这时就不是某个单独 Tool 能解决的了，而是需要有人负责多步决策，这时 Agent 才有价值。

### 1.4 Agent 的使用场景

结合官方关于 **workflow vs agent** 的区分来理解。**Workflow（工作流）** 指步骤提前确定、执行顺序相对稳定的处理路线，例如先做 A，再做 B，再做 C，中间不需要模型临场决策。

区分：workflow 的流程基本固定，重点是”按既定步骤执行”；agent 的流程不完全固定，重点是”根据上下文动态决策”。**流程路径固定时，优先考虑工作流或链，而不是 Agent。**

比如：

- 固定先做文本切分，再做向量化，再写入向量库
- 固定先分类，再摘要，再存库
- 固定按 A → B → C 的顺序执行

这类场景更像 [第 15 章 LCEL 与链式调用](/stage3-framework/ch15) 或后续 LangGraph 的**工作流**问题。

**如果下一步怎么做不固定，需要模型根据中间结果动态决定，就更适合 Agent。**

比如：

- 用户问题不确定，需要模型决定先查库还是先调 API
- 工具很多，模型要自己选哪个
- 可能要调一次工具，也可能要调很多次
- 工具返回后还要继续推理

判断标准：

| 场景                                                   | 更适合什么  |
| ------------------------------------------------------ | ----------- |
| 路径固定、步骤明确、顺序可提前写死                     | 链 / 工作流 |
| 路径不固定、工具选择依赖上下文、中间结果会影响后续决策 | Agent       |

因此，很多企业项目采用混合模式：**Workflow 负责固定骨架，Agent 负责不确定节点的决策。**

Agent 的典型场景已从”会调几个工具”扩展到更完整的任务闭环：

- **浏览器自动化 / Computer Use Agent**：根据目标理解页面、点击按钮、填写表单、滚动页面，并通过截图或页面状态校验结果。
- **长任务研究代理**：围绕复杂问题拆分子任务，多轮搜索、交叉验证资料，最后生成带来源的结构化报告。
- **代码库维护代理**：读取代码库、定位相关文件、制定修改计划、编辑代码、运行测试，并根据失败结果继续修复。
- **文件 / 数据分析代理**：读取表格、PDF、日志或业务数据，调用代码执行、SQL、统计或可视化工具，输出分析结论和图表。

这些例子仍然符合上面的判断标准：流程固定用链或工作流，每一步都要根据中间结果判断才用 Agent。

## 2、演变过程：从多步组装到一步创建

### 2.1 V0.3 / classic 路线：显式组装 Agent

较早的 LangChain Agent 写法需要显式准备五部分：模型、工具列表、Prompt 模板、`create_tool_calling_agent(...)`、`AgentExecutor(...)`。

Agent 本身只负责决策——判断调用什么工具；**AgentExecutor** 负责驱动循环、执行工具、把结果写回上下文。

优点：结构清楚，容易看懂 Agent 和 Executor 的配合。局限：代码更长，Prompt、scratchpad、executor 等概念需要同时理解。

仓库里的 `AgentSmartSelectV0.3.py` 就是这条路线的典型案例。

### 2.2 V1.x 路线：create_agent 一步创建

到了 LangChain 1.x，官方更推荐的主线入口是：

```python
from langchain.agents import create_agent
```

然后直接把模型、工具、系统提示等交进去，得到一个可运行的 Agent。

核心变化不是”Agent 不循环了”，而是：**原来要显式组装的部分，被封装进了更统一的运行时。**

`create_agent` 背后使用的是**基于 LangGraph 的 graph-based runtime**：

- 当前消息和中间结果构成**状态**
- 下一步是继续推理、调工具还是结束输出，构成**状态流转**
- 整个过程是一张”节点 + 连线”的执行图，所以叫 **graph-based**

**`create_agent` 看起来像一步创建，但底层仍然有完整的循环、状态、工具调用运行时在支撑。** Agent 仍然在循环、调工具、维护消息状态，只是不再要求手动拼出 `Agent + AgentExecutor + scratchpad` 才能跑。

### 2.3 这两条路线的意义

两条路线各有教学价值：

- **V0.3 / classic 路线**：帮助理解 Agent 内部运转——Prompt、工具、Executor、循环如何配合。
- **V1.x / `create_agent` 路线**：对应当前官方主线写法，更接近真实项目开发。

本章的目的是：**经典写法怎么看，当前写法怎么用，二者背后的 Agent 本质是同一件事。**

下图展示了从组件输入到 Agent 创建的整体流程：

![三步组装智能体示意：① 定义工具（如 `tools = [get_weather]`）② 构建系统提示 ③ 调用 `create_agent(model, tools, system_prompt)` 将 Tools / Prompt / Model 收口为可运行 Agent](/images/21/21-2-1-1.jpeg)

### 2.4 V0.3 与 V1.x 的对比速览

| 维度       | V0.3 / classic                                | V1.x / `create_agent`  |
| ---------- | --------------------------------------------- | ---------------------- |
| 核心入口   | `create_tool_calling_agent` + `AgentExecutor` | `create_agent`         |
| 代码组织   | 手动拼更多组件                                | 统一入口更简洁         |
| 学习价值   | 更容易看清内部结构                            | 更接近当前官方主线     |
| 运行时心智 | Agent 决策，Executor 驱动循环                 | graph runtime 驱动循环 |
| 更适合     | 理解原理、维护旧案例                          | 新项目、快速搭建       |

补充：**当前官方 1.x 文档更强调以 `messages` 状态作为 Agent 的统一输入。** 本仓库为保持教学连续性，仍保留了部分 `{“input”: “...”}` 风格示例。两种写法本质上都是给 Agent 一个新的用户请求，只是不同版本的调用入口略有差异。

## 3、Agent 工作原理（V0.3）

本节聚焦 classic 路线，因为它最适合拆开理解 Agent 的内部工作机制。

### 3.1 为什么还要学 V0.3

新项目通常直接用 `create_agent`，但 classic 路线能让你看清楚：Agent 负责什么，AgentExecutor 负责什么，Prompt 里为什么要有 `agent_scratchpad`，工具结果是怎么”再喂回去”给模型继续推理的。

### 3.2 Agent 与 AgentExecutor 的职责分工

在 V0.3 / classic 路线下，职责可以直接拆成：

- **Agent**：负责分析输入、决定下一步动作
- **AgentExecutor**：负责执行动作、拿结果、继续驱动循环

**Agent 是大脑，AgentExecutor 是执行器和循环调度器。** 单独有 Agent 不够，还需要 Executor 来驱动执行。

下图展示了这种分工：

![AgentExecutor 工作流示意：左侧为消息流（Input、模型回复、History）；中间为 Agent 链（Prompt、LLM、输出解析）决定下一步；右侧为可调用的 Tool 1…n，执行结果回传并形成循环直至结束](/images/21/21-3-1-1.jpeg)

### 3.3 agent_scratchpad 重要性

你在 classic 路线里经常会看到 Prompt 里有这样一个占位：

```python
("placeholder", "{agent_scratchpad}")
```

其中 `ChatPromptTemplate`、占位符与消息结构，与 [第 13 章 提示词与消息模板](/stage3-framework/ch13) 一脉相承；这里多出来的 `{agent_scratchpad}` 专供多轮工具循环使用。

它是 Agent 的”草稿区 / 中间步骤区”，用来承接：模型上一轮决定调用什么工具、工具返回了什么、下一轮模型基于这些信息继续推理。

没有这块区域，模型就无法在多步循环里”记住自己做过什么”。在 classic 路线里，`agent_scratchpad` 是 **ReAct 循环能成立的关键拼图**。

### 3.4 结合案例理解

【案例源码】`案例与源码-2-LangChain框架/12-agent/AgentSmartSelectV0.3.py`

[AgentSmartSelectV0.3.py](https://github.com/didilili/ai-agents-from-zero/blob/main/案例与源码-2-LangChain框架/12-agent/AgentSmartSelectV0.3.py ":include :type=code")

这个案例展示了 classic Agent 的完整链路：

1. 定义 `get_weather` 工具
2. 定义 `ChatPromptTemplate`
3. 在 Prompt 里保留 `agent_scratchpad`
4. 用 `create_tool_calling_agent` 得到 Agent
5. 用 `AgentExecutor` 驱动执行

当用户问：请问今天北京和上海的天气怎么样，哪个城市更热？

Agent 的执行过程：

1. 先判断需要查天气
2. 调一次 `get_weather(Beijing)`
3. 再调一次 `get_weather(Shanghai)`
4. 根据两次工具结果做比较
5. 最后输出总结

这个案例演示的不是”天气查询”本身，而是：**classic Agent 如何做多步工具调用，并把多次结果汇总成最终回答。**

## 4、Agent 工作原理（V1.0）

本节对应当前官方主线。

### 4.1 create_agent 的意义

`create_agent` 的价值在于：**把 Agent 的常见配置收口到一个统一入口。** 传入模型、工具、系统提示，有时再加结构化输出、状态、中间件，就能得到一个可运行的 Agent。开发者可以更专注于业务目标，而不是底层组装细节。

### 4.2 V1.x 的核心输入

入门阶段，`create_agent` 最常用的 6 个参数：

| 参数              | 是否常见     | 作用                                         |
| ----------------- | ------------ | -------------------------------------------- |
| `model`           | 必备         | 让谁来做推理与决策                           |
| `tools`           | 很常见       | 给 Agent 哪些可调用能力                      |
| `system_prompt`   | 很常见       | 约束 Agent 的角色、风格和工作规则            |
| `response_format` | 很常见       | 让最终结果更适合结构化输出                   |
| `checkpointer`    | 进阶但很重要 | 保存运行状态，可支撑短期记忆                 |
| `middleware`      | 进阶但很重要 | 在模型调用、工具调用等阶段插入自定义控制逻辑 |

前四个最适合入门；后两个偏工程化能力。

### 4.3 结构化输出在 Agent 中的理解

**Agent 不只能返回自然语言，也可以返回结构化结果**——JSON、TypedDict、Pydantic 对象等便于程序直接消费的字段结构。`response_format` 正是控制这一能力的参数。

在当前 1.x 文档语境里，`response_format` 常见有三种理解方式：

- 直接传 schema 类型：例如 `TypedDict`、Pydantic 模型，框架会按模型能力自动选择更合适的结构化输出策略。
- 显式 `ProviderStrategy(schema)`：当底层模型原生支持结构化输出时，更贴近 provider 原生能力。
- 显式 `ToolStrategy(schema)`：把结构化输出当成一次工具调用式约束，兼容性通常更好。

**`response_format` 不是后处理式的”把字符串转 JSON”，而是在 Agent 最终输出阶段提前约束结果的结构。**

### 4.4 checkpointer、thread_id 与短期记忆

给 `create_agent` 传入 `checkpointer`，底层运行时就能保存 Agent 的状态，使其可以在多轮调用之间保留上下文。

三个关键概念：

- **checkpointer**：状态保存器，负责把运行过程中的状态记下来
- **thread_id**：一次会话或一条对话线程的标识
- **短期记忆**：在同一个 `thread_id` 下，多轮消息和状态能够被延续使用

**checkpointer 决定”状态能不能存下来”，thread_id 决定”这些状态属于哪一条会话”。**

> **版本说明：** 在 LangChain 1.x 语境里，`thread_id` 主要服务于 checkpointing 和多轮状态隔离；如果要传用户资料、租户信息、权限上下文等静态运行时信息，还需要关注 `create_agent` 的 `context` 等上下文机制，不要把所有业务信息都塞进 `thread_id`。

与 [第 16 章 记忆与对话历史（含Redis基础）](/stage3-framework/ch16) 关联：第 16 章偏”记忆是什么、怎么存历史消息”，本节偏”在 1.x 主线上，状态和短期记忆怎么接进 Agent 运行时”。

### 4.5 运行过程怎么观察：stream 与 LangSmith

Agent 往往不是一步完成的，只用 `invoke()` 不够。

#### 4.5.1 stream() 的价值

Agent 经历模型判断、工具调用、工具返回、再次判断、最终输出等多步过程。`invoke()` 要等到最后才能看到结果，而 `stream()` 能**把中间进展实时暴露出来**：

- 看到 Agent 到底卡在模型还是工具上
- 看到是否发生了多轮工具调用
- 给前端提供更好的交互体验
- 调试“为什么这次 Agent 没按预期走”

`invoke()` 等最终结果，`stream()` 看执行过程。

#### 4.5.2 LangSmith 与 Agent

Agent 的调试问题往往不是”有没有报错”，而是：

- 为什么调了这个工具而不是那个
- 为什么多调了一轮
- 为什么结构化输出没按预期生成
- 为什么这一步耗时特别长

这些问题只看最后一句回答是不够的。**LangSmith** 是官方提供的可观测平台，用于追踪、调试、测试、评估 Agent 运行过程。

`stream()` 在代码层面看过程，LangSmith 在可视化层面看过程，两者互补。

### 4.6 结合案例理解

【案例源码】`案例与源码-2-LangChain框架/12-agent/AgentSmartSelectV1.0.py`

[AgentSmartSelectV1.0.py](https://github.com/didilili/ai-agents-from-zero/blob/main/案例与源码-2-LangChain框架/12-agent/AgentSmartSelectV1.0.py ":include :type=code")

这个案例和 V0.3 做的是同一类业务：都是围绕“北京和上海谁更热”来调用天气工具。

教学重点不再是 Prompt + Executor 的手工组装，而是：

- `create_agent(...)` 的统一创建方式

读这个案例时，关注两件事：

1. **为什么代码明显更短了**
2. **为什么最后可以直接拿到 `structured_response`**

这两点正好代表了 V1.x 路线的两个现实价值：更适合新项目快速搭建；更适合把 Agent 输出接进后端业务逻辑。

另外，虽然本教程里的 `AgentSmartSelectV1.0.py` 重点放在 `invoke()` 和结构化输出上，但如果放到真实项目里，你通常还会继续关心：

- 要不要用 `checkpointer` 保留短期记忆
- 要不要通过 `middleware` 做动态控制和守护

`create_agent` 看起来只是一个函数，背后可以延展到完整的 Agent 工程化能力。

总体差异已在上文 **2.4 节（V0.3 与 V1.x 对比速览）** 从 API 与运行时角度概括过；下表仅对照本仓库**同一业务（双城气温比较）**下的两个文件，便于你并排阅读代码。

| 维度     | `AgentSmartSelectV0.3.py`               | `AgentSmartSelectV1.0.py`            |

### 5.2 ReAct 实操

【案例源码】`案例与源码-2-LangChain框架/12-agent/AgentReact.py`

[AgentReact.py](https://github.com/didilili/ai-agents-from-zero/blob/main/案例与源码-2-LangChain框架/12-agent/AgentReact.py ":include :type=code")

这个案例用来建立”**Agent 会自己连续做多步决策**”的直觉。

它定义了两个工具：

- `search_products`
- `check_inventory`

用户的问题不是简单的“查某个 ID 是否有库存”，而是：查找当前最受欢迎的无线耳机并检查是否有库存。

### 5.3 A2A 实操

【案例源码】`案例与源码-2-LangChain框架/12-agent/Agent2Agent.py`

[Agent2Agent.py](https://github.com/didilili/ai-agents-from-zero/blob/main/案例与源码-2-LangChain框架/12-agent/Agent2Agent.py ":include :type=code")

这个案例对应的是多智能体协作，也就是常说的 **A2A（Agent-to-Agent）**。

它把”一个 Agent 解决所有问题”换成了分工思路：携程 Agent 只负责机票，美团 Agent 只负责酒店，滴滴 Agent 只负责打车，最上面有一个总协调逻辑负责调度。

这贴近真实项目。企业级系统里，往往不是一个大而全的 Agent，而是：

- 一个总入口
- 多个领域专长子 Agent
- 各自有边界
- 最后再汇总结果

补充：**官方多智能体资料里，常见做法是把 subagent 包装成 tool，再交给主 Agent 调用。**

而本教程里的这个案例，使用的是：

- 子 Agent 链
- `RunnableLambda` 协调
- 显式顺序调度

这不是错误，而是另一种教学表达方式，能更清楚地看到：子 Agent 如何单一职责，总协调如何串联业务顺序。**多智能体协作的重点不是 API 长什么样，而是”分工 + 协调”。**

### 5.4 Agent + MCP 实操

这个案例把第 20 章 MCP 和本章 Agent 接上了。前面的工具都是当前进程里直接写的 `@tool`，而这个案例演示：**工具可以来自外部 MCP 服务。**

## 6、小结：Agent、Tool、Function Calling、RAG、MCP 的区别与联系

这些概念最容易混淆，需要统一梳理。

> **术语约定：** 为和前文保持一致，本章这里写 **Function Calling** 是因为它在很多官方资料里仍然常见；如果你更习惯 [第 17 章](/stage3-framework/ch17) 的说法，也可以直接把它理解成 **Tool Calling 这层调用机制**。

### 6.1 总表

| 概念                 | 它解决什么问题                      | 定位         |
| -------------------- | ----------------------------------- | ------------ |
| **Tool**             | 系统有哪些可调用能力                | 能力层       |
| **Function Calling** | 模型怎么把“调工具”表达出来          | 调用机制     |
| **RAG**              | 模型缺知识时怎么拿上下文            | 上下文增强   |
| **MCP**              | 工具 / 资源 / Prompt 怎么标准化接入 | 连接协议     |
| **Agent**            | 什么时候用什么能力、按什么顺序做    | 决策与编排层 |

### 6.2 在真实项目里怎么配合

完整链路：

1. 用户提出一个目标
2. **Agent** 先判断该怎么做
3. 如果缺知识，就先走 **RAG**
4. 如果缺动作能力，就通过 **Function Calling** 去调 **Tool**
5. 这些 Tool 可能是本地写的，也可能来自 **MCP**
6. Agent 再根据返回结果继续判断，直到最终完成任务（需设好迭代上限与超时，避免死循环）

关系简写：

- **Agent = 决策层**
- **Tool = 能力层**
- **Function Calling = 调用机制**
- **RAG = 上下文增强**
- **MCP = 外部能力接入协议**

---

**章节思考题：**

1. 一个任务是否需要 Agent，你会看哪些信号？

   **参考思路：** 看任务是否步骤不固定、需要多次决策、需要动态选工具。固定输入到固定输出的场景用链或工作流更简单。

2. Agent、Tool、RAG、MCP 放在一起时，各自的位置是什么？

   **参考思路：** Agent 决策，Tool 执行，RAG 补知识，MCP 标准化接入。它们不互相替代，而是分层协作。

3. 为什么 Agent 系统一定要设置迭代上限、超时和失败处理？

   **参考思路：** 没有边界时可能循环调用、成本失控或执行危险动作。必须有停止条件、错误兜底和日志追踪。

4. 旧的 AgentExecutor 和新的 `create_agent` 思路，你会怎样看待它们？

   **参考思路：** 旧写法帮助读懂历史代码，新写法贴近当前主线。根据项目版本和维护成本选择。

**本章小结：**

- **Agent 的核心定位是决策层**：让系统围绕目标判断下一步做什么、是否调工具、工具结果回来后是否继续。Tool 是能力层，Agent 是协调层。
- **理解 Agent 的办法是放回 ReAct 循环里看**：观察问题、决定动作、调用工具、拿回结果、继续决策。这样再看 classic 路线的 scratchpad / AgentExecutor 和 1.x 路线的 `create_agent`，就不会只停留在 API 记忆。
- **LangChain 1.x 主线三个工程要点**：`response_format` 负责输出结构化，`checkpointer` 负责状态持久化，`thread_id` 负责会话隔离。三者决定 Agent 能否从演示走向系统可用。
- **什么时候不该上 Agent**：步骤固定、路径稳定、可控性要求高时，优先用 LCEL 或 Workflow。只有需要动态选工具、临场分解步骤、边执行边调整时，Agent 才值得引入。
- **可上线的 Agent 重点在边界**：工具白名单、参数校验、人审或二次确认、超时重试、日志与状态持久化，比多接几个 Tool 更关键。
