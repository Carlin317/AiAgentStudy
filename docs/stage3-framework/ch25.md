# 25 - LangGraph 高级特性

---

**本章课程目标：**

- 理解 LangGraph 的四类高级能力：**流式处理（Streaming）**、**状态持久化（Persistence）**、**时间回溯（Time-Travel）**、**子图（Subgraphs）**。
- 认识到这些能力构成 LangGraph 面向生产场景的基础设施——可观测、可恢复、可复用、可扩展。

## 1、流式处理（Streaming）

### 1.1 定义

LangGraph 的流式处理范围比普通 LLM token 流更大。它不仅输出模型生成过程，还能把**图执行过程中的状态变化、节点进度、子图过程、自定义消息**实时暴露出来。

两者的核心区别：

- **普通 LLM 流式**：关注模型文字的逐步输出
- **LangGraph 流式**：关注整张图的执行进度和状态变化

LangGraph Streaming 的本质是：**把图执行过程逐步呈现，而不是等整张图跑完才返回结果。**

### 1.2 为什么流式处理很重要

流式处理是 AI 应用的基础能力之一。真实项目里常见需求包括：

- 前端希望边执行边展示当前进度，而不是长时间白屏等待
- 调用大模型时，希望 token 级别实时显示
- 工作流较长时，希望知道当前执行到哪个节点
- 调试复杂图时，希望看到每一步到底更新了什么状态
- 子图或工具内部有重要中间结果，希望在最终结果出来前先看到过程

它的价值体现在两层：**用户体验层**——更快感知结果正在生成；**工程调试层**——更容易观察图内部执行过程。

### 1.3 stream() 和 invoke() 的区别

- `invoke()`：等整张图跑完，再返回最终结果
- `stream()` / `astream()`：图在运行过程中，把中间结果分批往外送

如果只关心最终结果，用 `invoke()`；如果想边执行边观察，用 `stream()` 或 `astream()`。

LangGraph 图实现了 **Runnable** 接口，因此天然具备流式能力，也能和 [LangChain `Runnable` / LCEL](/stage3-framework/ch15) 体系衔接。

`stream()` 并非只有一种输出格式。调用时通常需要配合 `stream_mode` 参数，决定图在执行过程中往外流什么——完整状态、增量更新、模型消息片段，还是自定义进度信息。

### 1.4 stream_mode 有哪些

LangGraph 通过 `stream_mode` 指定流的内容类型。当前常用模式：

| 模式       | 含义                                  |
| ---------- | ------------------------------------- |
| `values`   | 每一步结束后输出当前完整状态快照      |
| `updates`  | 每一步结束后只输出本步的增量更新      |
| `messages` | 输出 LLM 生成过程中的消息片段 / token |
| `custom`   | 输出节点内部主动写出的自定义消息      |
| `debug`    | 输出更完整、更底层的调试信息          |

如果需要同时接收多种流，可以传列表，例如：

```python
stream_mode=["updates", "custom"]
```

此时返回的流式结果会标注每条数据属于哪种模式。

### 1.5 values 和 updates 怎么区分

这两个模式容易混淆：

- `values`：每一步输出当前完整 State
- `updates`：每一步只输出本步改了哪些字段

`values` 是全量快照，`updates` 是增量日志。

## 2、状态持久化（Persistence）

### 2.1 定义

流式处理解决”图运行过程怎么被看见”，状态持久化则解决另一个问题：**图跑到一半或跑完之后，状态能否被保存并在下次继续使用。**

LangGraph 的持久化围绕 **checkpoint（检查点）** 展开：**给图配置 checkpointer 后，图在每一步都可以把当前状态保存为检查点。** 保存的字段与合并规则由 [第 23 章](/stage3-framework/ch23) 定义的 **State / Reducer** 决定。

检查点会被组织到某个 **thread** 下。入门阶段，thread 相当于”同一条会话或工作流链路”的 ID 容器，最常见的区分方式是：

```python
{"configurable": {"thread_id": "..."}}
```

以此区分不同对话、用户或执行线程。

![Checkpoint 持久化概念：自动存档、失败恢复、暂停与恢复、时间旅行与审计追踪（images/25/25-2-1-1.jpeg）](/images/25/25-2-1-1.jpeg)

**图注：** 上图概括 **Checkpoint 在生产场景中的价值**（存档、容错、断点续跑、回溯与审计）；`thread_id` 则用于在存储侧把同一对话/任务链的检查点归并到一条「线程」下，与图中「按步落盘」互补。

### 2.2 为什么持久化很重要

LangGraph 的多项高级能力都建立在持久化之上。官方文档明确指出，持久化是以下能力的基础：

- 人工介入（human-in-the-loop）
- 对话 / 线程级记忆
- 时间回溯（time-travel）
- 容错恢复（fault-tolerant execution）

持久化不是额外的存储层，而是 LangGraph 适合构建生产级 Agent / Workflow 的关键原因之一。

### 2.3 短期记忆：Checkpointer

LangGraph 语境里最先接触到的持久化组件是 **Checkpointer**。它的本质是：

- 按 `thread_id` 保存图的执行状态
- 让同一线程下的多次调用可以继续沿用之前的状态

Checkpointer 相当于**线程内、会话内、工作流运行期的短期记忆**。与前面章节讲的消息历史属于同一层短期记忆，区别在于这里保存的是**整张图的状态快照**。

### 2.4 长期记忆：Store / BaseStore

Checkpointer 偏向同一线程内部的连续状态。如果需要跨线程、跨会话保存长期信息，就需要 **Store**。

官方 Persistence 文档对此的定义是：**Checkpointer 保存线程内状态，Store 保存跨线程共享的长期信息。**

两者的核心区别：

- **Checkpointer**：保存图在某条 thread 里的运行状态
- **Store / BaseStore**：保存跨 thread、跨会话仍然要长期保留的数据

例如：

- 用户偏好
- 长期业务事实
- 跨会话共享的知识片段

这些都适合放 Store，而非塞进单条 thread 的 checkpoint 链。

### 2.5 持久化后端怎么选

从本地学习到真实部署，持久化后端的典型演进路线：

- **内存**：适合学习和临时验证
- **SQLite**：适合本地开发、小型项目、单机部署
- **Postgres / Redis / 其他数据库后端**：适合生产环境

入门阶段先掌握内存和 SQLite，生产部署时再选择 Postgres / Redis 等后端。

![持久化后端演进示意：内存 → SQLite → Postgres/Redis 等（动图）（images/25/25-2-5-1.gif）](/images/25/25-2-5-1.gif)

**图注：** 学习阶段多用内存 Checkpointer；本地与小型部署常用 SQLite；生产环境再按可用性与运维需求选用 Postgres、Redis 等官方或社区后端实现。

## 3、时间回溯（Time-Travel）

### 3.1 定义

时间回溯是 LangGraph 面向生产级工作流的一项能力。

它解决的问题是：**图已经跑过了，能否回到历史中某一步，从那里重新继续跑，甚至修改状态后再跑。**

这类需求在线性脚本里很难实现，但在 LangGraph 里因为已有 checkpoint 链，时间回溯自然就有了基础。

### 3.2 为什么时间回溯有价值

时间回溯的价值在于它适合处理**非确定性系统**，尤其是 LLM 驱动的 Agent / Workflow。

真实项目中常见的问题：这次为什么回答对了，需要回看中间过程；这次为什么跑偏了，需要定位哪一步开始出问题；如果在某一步换一个状态或分支，后续会怎样。

因此时间回溯的典型用途是：调试、复盘、分支探索、人工修正后重跑。

### 3.3 时间回溯通常怎么做

官方文档的思路可以收敛为四步：

1. 先跑一遍图，生成历史 checkpoint
2. 用 `get_state_history(...)` 找到你想回到的那个历史点
3. 视情况决定是原样恢复，还是先 `update_state(...)` 改状态
4. 再从那个历史点继续 `invoke(...)` 或 `stream(...)`

类比来看：先有历史录像，再选从哪一帧切回去，可选改一下剧本，然后从那里继续往后演。

### 3.4 案例：TimeTravel

这个案例的重点在于观察：

- 历史 checkpoint 如何被取出
- 目标 checkpoint 如何被选定
- 修改状态后，为什么会形成新的执行分支

时间回溯不是抹掉过去，而是**基于过去某个点分出一条新路径**。

## 4、子图（Subgraphs）

### 4.1 定义

当图变复杂时，一个自然的需求是：**能否把一整张图当成另一张图里的一个节点来复用？**

这就是子图要解决的问题：**把一个已编译的图嵌入到另一张更大的父图里。** 子图的价值在于复杂流程拆分、模块化复用、父子流程解耦。

![子图概念：父图中 Node_3 为 Sub_Graph，内含子流程；主图从 START→Node_1 分支至 Node_2 或子图，再汇聚至 END（注：图中起点标注有误，应为 START）](/images/25/25-4-1-1.jpeg)

### 4.2 为什么需要子图

当所有节点都堆在一张图里时，会出现图结构难读、局部流程无法单独测试、相似流程难复用、子模块之间耦合加重等问题。

子图类似”工作流层面的函数抽取”，可以和普通函数封装类比：

- 普通函数：把一段 Python 逻辑封起来复用
- 子图：把一段 LangGraph 工作流封起来复用

### 4.3 子图最常见的三种理解方式

子图有三种常见模式：

1. **最简单模式**：把编译后的子图直接当成父图里的节点
2. **共享字段模式**：父图和子图共享部分状态字段
3. **状态转换模式**：父图状态和子图状态结构不同，需要代理节点做转换

本章三个子图案例按此顺序递进。

### 4.4 案例：子图作为节点（SubGraphHello）

最基础的子图案例，核心观察点：

- 子图可以像普通节点一样被挂进父图
- 父图执行到该节点时，本质上在执行一整张子图

### 4.7 子图再往前走一步：和持久化、记忆的关系

官方子图文档还指出：**子图不只是结构复用问题，它和持久化、线程级状态、命名空间隔离也有关联。**

当前阶段先了解以下要点即可：

- 子图涉及持久化时，会带来父图 / 子图状态边界问题
- 子图要有独立记忆时，需要考虑 thread 级别与命名空间隔离
- 子图作为普通节点直接嵌入是最易理解的方式

**章节思考题：**

1. Streaming、Persistence、Time-Travel、Subgraph 这几个能力分别解决哪类真实痛点？

   **参考思路：** Streaming 解决过程不可见，Persistence 解决中断恢复，Time-Travel 解决回放调试，Subgraph 解决流程拆分和复用。

2. 为什么 `updates` 和 `values` 适合观察不同层面的信息？

   **参考思路：** `updates` 看每一步变了什么，适合调试节点行为；`values` 看某时刻完整状态，适合理解全局。排障时两者常结合使用。

3. Checkpointer 和 Store 的边界为什么要分清？

   **参考思路：** Checkpointer 保存线程执行状态，用于恢复和回放；Store 保存跨线程业务数据，用于长期复用。混用两者会导致系统难以维护。

4. 如果线上任务跑偏，Time-Travel 能帮你做什么，不能帮你做什么？

   **参考思路：** 它能回到某个 checkpoint 查看状态、复盘路径、从中间点重跑，但不能自动判断业务对错，也不能替代日志、评测和权限控制。

**本章小结：**

- **Streaming** 让图在执行过程中就能输出状态、消息、进度与调试信息，不必等执行完毕。
- **Persistence** 是 LangGraph 的核心生产能力。Checkpointer 管线程内状态，Store 管跨线程长期信息。
- **Time-Travel** 建立在持久化之上，从历史 checkpoint 恢复或修改后重跑，适合调试、复盘和分支探索。
- **Subgraphs** 让复杂工作流可以模块化拆分和复用，是从小图走向大系统的关键一步。
- 学完本章后，应能说清 `stream()` 和 `invoke()` 的区别以及五种流式模式各自的用途；知道 Checkpointer 和 Store 的边界；理解 Time-Travel 依赖持久化，Subgraph 是结构复用而非单纯拆文件。
