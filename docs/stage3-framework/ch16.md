# 16 - 记忆与对话历史（含 Redis 基础）

---

**本章课程目标：**

- 理解本章所说的**记忆（Memory）**到底是什么，知道它为什么在多轮对话中不可缺少。
- 掌握“**读历史 → 拼入提示 → 调模型 → 写回历史**”这条最核心的实现主线，理解 `RunnableWithMessageHistory` 与 `BaseChatMessageHistory` 的职责分工。
- 对 Redis 在本章中的定位建立清晰认识：它不是让模型“变聪明”，而是让**会话历史可持久化、可跨进程、可跨实例共享**。

**学习建议：** 建议用两轮对话来体会：先观察无记忆时模型为什么”忘事”，再观察同一 `session_id` 下历史消息的读取、注入、调用和写回过程。Redis 只是存储后端，核心是”读历史 → 拼提示 → 调模型 → 写历史”这条主线。

**官方文档与资源**：详见 [工具导航与参考资料索引 - LangGraph](/guide/resources#LangGraph)。

## 1、记忆简介

### 1.1 为什么需要记忆

如果你只做单轮问答，那么每次请求都是一次独立调用，模型只看当前输入，答完就结束。  
但只要你开始做聊天机器人、客服助手、学习助手、企业知识问答，多轮上下文就会立刻成为刚需。

最典型的现象就是：

1. 第一轮你说：“我叫张三。”
2. 第二轮你再问：“我叫什么？”

如果系统没有保存并重新注入上一轮内容，模型就只能把第二轮当作一条全新的请求，于是很自然地回答：“我不知道。”这不是模型“太笨”，而是程序根本没有把上一轮信息带给它。

![无记忆时两轮对话相互独立，模型无法利用上一轮信息](/images/16/16-1-1-1.jpeg)

所以从工程角度看，记忆并不是一个“可有可无的高级特性”，而是多轮对话系统最基础的能力之一。它至少解决三类问题：

- **上下文连续性**：让模型知道上一轮说过什么。
- **会话个性化**：让模型记住用户在当前会话里提供的信息，如名字、偏好、任务背景。
- **多步任务承接**：让模型把前一步结果作为后一步输入，而不是每轮都重新从零开始。

![LangChain 官方文档「Core components → Short-term memory」概述：记忆用于保存先前交互信息，支撑智能体在多轮交互中保持效率与体验](/images/16/16-1-1-2.jpeg)

### 1.2 定义

本章里的**记忆（Memory）**，指的主要是**短期记忆（Short-Term Memory）**或**对话历史（Chat History）**。

它的本质不是“模型真的记住了”，而是：**程序把之前的消息保存下来，并在下一轮调用前，再把这些历史消息一并传给模型。**

从工程角度看，它是外部会话状态管理机制，与模型参数更新无关。

### 1.3 这不是训练模型

容易和模型训练混淆。本章的记忆**不是**重新训练模型、不是把信息写进模型参数、不是让模型永久学会知识。

它做的事只是：把历史消息保存在外部，下次调用前重新读出来，和当前问题一起发给模型。模型”记住你是谁”，是因为程序每次都把”你叫张三”这条历史重新带给它。

因此：内存版程序一关历史就丢，Redis 版程序重启后历史还能读回来。

### 1.4 本章的“记忆”能做什么

从项目角度看，本章的记忆主要能做这些事：

- **让多轮问答连续起来**：例如先自我介绍，再追问名字、偏好、之前说过的内容。

- **保存当前会话上下文**：例如用户正在做一份简历、正在学习 Python、正在整理某份报告，后续问题不必每轮都重述背景。

- **为链式流程提供上下文**：历史消息最终通常通过 [第 13 章](/stage3-framework/ch13) 的 `MessagesPlaceholder` 注入模板，与 [第 15 章](/stage3-framework/ch15) 中的链组合在一起使用。

- **为后续 Agent / Tool / LangGraph 打基础**：你后面会发现，工具调用、Agent、多步决策几乎都离不开“当前线程 / 当前会话”的状态保存。

### 1.5 本章不重点讨论什么

为了避免和后面章节混在一起，这里也要明确本章边界：

- **不是长期知识记忆**：比如用户永久画像、跨很多天的长期偏好管理，这不属于本章核心。

- **不是 RAG 检索记忆**：把外部文档查出来再回答，属于 [第 19 章 RAG](/stage3-framework/ch19) 的主线。

- **不是 Agent 决策状态机**：更复杂的循环式状态与持久化，会在 [Agent](/stage3-framework/ch21) 与 LangGraph 相关章节里更自然地出现。

**本章主要讲：当前会话里，怎么把历史消息保存起来并重新注入给模型。**

## 3、实现原理

### 3.1 核心主线

记忆的实现原理可以压缩成四步：

1. **读历史**
2. **把历史拼进当前提示**
3. **调用模型**
4. **把本轮输入和输出写回历史**

这就是本章最核心的主线。

![记忆在链中的位置：读历史 → 拼入 Prompt → 调模型 → 写回历史](/images/16/16-3-1-1.jpeg)

### 3.2 工程化表达

如果用更接近程序的方式来描述，一次带记忆的调用通常是这样发生的：

**第一步：根据会话标识找到对应历史。**  
比如通过 `session_id="user-001"` 找到这位用户当前会话的消息列表。

**第二步：把历史消息插入 Prompt。**  
这一步通常会和 [第 13 章](/stage3-framework/ch13) 里的 `MessagesPlaceholder("history")` 配合使用。

**第三步：把“历史 + 当前问题”一起交给模型。**  
这样模型看到的就不再只是当前一句话，而是完整上下文。

**第四步：把本轮消息写回历史存储。**  
也就是把：用户这一轮输入、模型这一轮回复，都追加进去，供下一轮再读取。

### 3.3 MessagesPlaceholder 与模板的关系

在对话历史场景里，你通常不会把历史消息一条条手写死在模板中，因为历史轮数与内容每轮都在变。更合理的做法是在模板里留一个“历史消息插槽”，运行时再把当前会话历史整块塞进去——这正是 [第 13 章](/stage3-framework/ch13) 中 `MessagesPlaceholder` 的典型用法，与本章的“读写历史”前后衔接。

### 3.4 session_id 的意义

只要涉及记忆，就会涉及一个关键问题：**你怎么知道哪份历史属于哪位用户、哪次会话？**

最常见的做法就是使用 `session_id`，它就是“当前会话的编号”。

例如：

- `user-001`
- `user-002`
- `chat-room-a`

不同的 `session_id`，通常对应不同的历史记录。

这也是为什么本章 Redis 版和多 session 版案例里，`session_id` 都很重要。如果没有这层区分，系统就可能把 A 用户的历史错拿给 B 用户。

### 3.5 本章和 LangGraph 官方主线的关系

LangChain / LangGraph 当前官方主线里，**短期记忆**越来越倾向于放在 **LangGraph persistence / checkpointer / thread** 体系中。官方更强调：

- 线程（thread）
- 持久化（persistence）
- 检查点（checkpointer）
- 图执行状态

但 `RunnableWithMessageHistory` 仍有价值：更直观，对 LCEL 链更容易理解，对”记忆本质是历史消息注入”这件事讲得最透明。

本章的教学路线：先学 `RunnableWithMessageHistory + BaseChatMessageHistory`，同时了解官方更大主线已转向 LangGraph persistence。

> **版本说明：** 本章继续使用 `RunnableWithMessageHistory`，是为了把 LCEL 链里的“历史消息如何读写和注入”讲清楚。生产级 Agent 或复杂多轮状态管理，建议再对照 LangGraph 的 checkpointer、thread 和 persistence 机制来设计。

**补充：** 历史消息占用模型上下文窗口；轮数过多时需要做截断、摘要或只保留最近 k 轮，避免触达 token 上限或成本上升。本章先建立”注入历史”的主线。

## 4、实现类介绍：RunnableWithMessageHistory 与 BaseChatMessageHistory

### 4.1 本章应抓哪条主线

本章技术线：

- **课程案例主线**：`RunnableWithMessageHistory + BaseChatMessageHistory`
- **官方当下更大的主线**：LangGraph short-term memory / persistence

先掌握课程案例主线，它能帮助理解历史的读取、注入和写回机制。

### 4.2 ConversationChain（早期写法）

LangChain 早期的 `ConversationChain` 内置了对话模板和记忆机制，适合快速演示，但灵活性有限，不贴合 LCEL / Runnable 体系，已不适合作为主线学习对象。

### 4.3 RunnableWithMessageHistory（更合适的写法）

`RunnableWithMessageHistory` 给已有的 Runnable / Chain 包上一层历史管理能力，不替代 Prompt、Model、Parser，而是在它们外面统一负责历史的读取、注入和写回。它在 Runnable 体系之上工作，与第 15 章的 LCEL 自然衔接。

### 4.4 BaseChatMessageHistory（历史存储接口）

`BaseChatMessageHistory` 解决”历史存在哪里、怎么存”，是聊天消息历史的统一抽象接口。

分工明确：`RunnableWithMessageHistory` 控制历史何时读写，`BaseChatMessageHistory` 及其实现类控制历史存到哪里。

### 4.5 常见实现类

LangChain 提供了多种聊天历史实现（如内存、文件、Redis、Elasticsearch、DynamoDB 等），核心差别主要在于**是否持久化、是否适合多实例共享**。

常见实现：

| 组件名称                     | 存储方式     | 适合什么场景                   |
| ---------------------------- | ------------ | ------------------------------ |
| `InMemoryChatMessageHistory` | 进程内内存   | 本地学习、单进程演示、临时会话 |
| `FileChatMessageHistory`     | 本地文件     | 轻量持久化、小型脚本           |
| `RedisChatMessageHistory`    | Redis        | 持久化、跨进程、多实例共享     |
| 其他后端实现                 | ES、数据库等 | 和现有技术栈集成               |

学习顺序：先学 InMemory（最直观），再学 Redis（贴近真实项目）。

### 4.6 本章案例结构对应关系

学习路径：

| 文件                                     | 作用                              |
| ---------------------------------------- | --------------------------------- |
| `01_Memory_IDontKnow.py`                    | 先看无记忆时的问题                |
| `05_Memory_RunnableWithMessageHistory.py`   | 最基础的内存版带历史对话          |
| `06_Memory_RunnableWithMessageHistoryV2.py` | 多 session 版，对应真实多用户场景 |

编排逻辑：先看到问题 → 最简单解决方案 → 扩展到多 session → 持久化。

### 5.2 持久化：Redis 存储

内存版的问题是程序一重启历史就没了。Redis 在本章的角色很明确：不是模型、不是 Prompt、不是更高级的记忆算法，只是一个适合持久化保存会话历史的存储后端。从内存版切到 Redis 版，变化的是”历史保存的位置”，不是记忆原理。

#### 5.2.1 设计要求与参考文档

目标：**把对话历史从进程内存换成 Redis 持久化存储**，实现程序重启后恢复历史、多实例共享。

同时结合本项目当前依赖，你也要知道：

- 本仓库 `requirements.txt` 中已经包含 `redis>=5.3,<6`
- 也包含 `langchain-redis>=0.2`

所以如果你已经执行过 `pip install -r requirements.txt`，通常不需要再单独补装基础依赖。

#### 5.2.2 Redis 与 Redis Stack 简介

**本章对话历史案例，原生 Redis 就够用了。** `RedisChatMessageHistory` 只使用 Redis 基础数据结构能力。Redis Stack 也能跑，且可以用 RedisInsight 可视化查看数据。

![Redis Stack 与原生 Redis 的关系](/images/16/16-5-2-2-1.jpeg)

`Redis` 是高性能键值存储本体，`Redis Stack` 在此基础上补上增强能力和更友好的工具链。本章保留 Redis Stack 小节，是为了用 RedisInsight 观察数据，也为后续向量存储等用法做环境铺垫。

| 功能维度 | 原生 Redis                 | Redis Stack 增强功能                                  |
| :------- | :------------------------- | :---------------------------------------------------- |
| 数据结构 | 字符串、列表、集合、哈希等 | 增加 JSON、图、时间序列、概率结构等高级类型           |
| 查询能力 | 仅限键值查询               | 支持全文搜索、向量搜索、图查询、JSON 查询             |
| 使用场景 | 缓存、消息队列、计数器等   | 实时推荐、时序分析、知识图谱、文档数据库、AI 向量检索 |
| 开发体验 | 命令行操作，需手动拼装逻辑 | 提供 RedisInsight 和对象映射库，开发效率更高          |

#### 5.2.3 Docker 启动与宿主机连接

本机没装 Redis 的话，用 Docker 最方便。

**原生 Redis：**

```bash
docker run -d --name docker-redis-1 -p 6379:6379 redis
```

这样本机就可以通过：

```bash
redis://localhost:6379
```

来连接 Redis。

**Redis Stack：**

```bash
docker run -d --name redis-stack -p 26379:6379 -p 8001:8001 redis/redis-stack
```

两个端口：`26379` 是本机访问 Redis 服务的映射端口，`8001` 是浏览器访问 RedisInsight 的端口。案例中连接 `redis://localhost:26379` 连的是宿主机映射端口。实际端口以 `docker ps` 为准。

#### 5.2.4 Redis 基本命令与查看对话历史

只需要会查看本章案例写入的数据即可。常用命令：

| 命令                 | 说明                       | 示例                             |
| :------------------- | :------------------------- | :------------------------------- |
| `PING`               | 检测服务是否存活           | `PING` → 返回 `PONG`             |
| `SET key value`      | 设置字符串键值             | `SET mykey "hello"`              |
| `GET key`            | 获取字符串值               | `GET mykey`                      |
| `DEL key [key ...]`  | 删除一个或多个键           | `DEL mykey`                      |
| `KEYS pattern`       | 按模式查找键（慎用于生产） | `KEYS *`、`KEYS message_store:*` |
| `EXISTS key`         | 判断键是否存在             | `EXISTS mykey` → 1 或 0          |
| `TTL key`            | 查看键的剩余过期时间（秒） | `TTL mykey`，-1 表示永不过期     |
| `EXPIRE key seconds` | 设置键的过期时间           | `EXPIRE mykey 3600`              |
| `DBSIZE`             | 当前数据库的键数量         | `DBSIZE`                         |
| `FLUSHDB`            | 清空当前数据库（慎用）     | `FLUSHDB`                        |

**LangChain 按 `session_id` 写入不同的键。** 运行 `session_id=user-001` 的会话后，可以查看：

```redis
KEYS *
TYPE message_store:user-001
LRANGE message_store:user-001 0 -1
```

每个元素就是一条序列化后的消息记录。**对话历史落到 Redis 里，就是按 session 管理的一组消息数据。**

**章节思考题：**

1. 如果用户说“模型记住了我”，你会怎样解释本章里的“记忆”到底是什么？

   **参考思路：** 记忆不是模型参数更新，而是系统把历史消息取出来作为上下文交给模型。

2. `RunnableWithMessageHistory` 和具体存储类的边界为什么要分清？

   **参考思路：** 前者负责何时读写，后者负责存在哪里。边界分清后，存储可替换而调用链逻辑不用大改。

3. 多用户场景里，`session_id` 设计不好会出现什么问题？

   **参考思路：** 可能串会话、串用户、泄露隐私。`session_id` 应与用户、会话、业务租户等隔离策略一起设计。

4. 为什么完整历史不能无限塞回模型？

   **参考思路：** 上下文窗口、成本、延迟和噪声都会增加。需要做窗口截断、摘要、重要信息提取和过期清理。

**本章小结：**

- **记忆**：短期记忆 / 对话历史，不是训练模型，而是把历史消息保存在外部并在下一轮重新注入。
- **实现主线**：”读历史 → 拼入提示 → 调模型 → 写回历史”。`MessagesPlaceholder` 留位置，`RunnableWithMessageHistory` 管读写时机，`BaseChatMessageHistory` 管存储。
- **内存版与 Redis 版**：`InMemoryChatMessageHistory` 适合单进程演示，`RedisChatMessageHistory` 适合持久化和多实例共享。
- **与官方主线**：课程用 `RunnableWithMessageHistory + BaseChatMessageHistory`，官方更大主线已转向 thread、persistence 和 checkpointer。
- 学完本章应明白记忆是外部保存和回填历史消息，能用四步概括实现主线，知道内存版与 Redis 版的适用场景及 `session_id` 的作用。

**建议下一步：** 跑通无记忆、内存版、多 session 版、Redis 版案例，观察同一 `session_id` 下历史的延续；然后学习 [第 17 章 Tools 工具调用](/stage3-framework/ch17)。
